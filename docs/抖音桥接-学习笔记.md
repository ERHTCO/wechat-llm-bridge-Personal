# 抖音桥接项目：能学什么（读 `pcmxiao/dsh-douyin-bridge`）

MIT，纯 JS 源码，克隆在 `../douyin-bridge/`。看完之后**只有一条技术值得抄**，
另外几条是教训。

## 它怎么读抖音私信

不逆向 `a_bogus`，也不碰 DOM：

```
页面里 hook fetch/XHR  →  抖音自己签名、自己请求  →  我们把响应截下来
                       →  用通用 protobuf 线格式解码（不需要 .proto）
```

两个关键设计：

1. **让应用自己发请求。** 签名、cookie、风控参数全由浏览器负责；代价是得先「触发」
   一次请求（打开私信面板 / 切会话），数据才来。**不自己拼带签名的请求**一直是它的主线。
2. **不需要 .proto 也能解 protobuf**（`lib/pb.mjs`）：每个字段是
   `(field number, wire type, value)`；wire type 2 的内容试着当嵌套消息解一遍，
   能刚好吃完 buffer 就是嵌套消息，否则当字符串。于是得到一棵无名但有形的字段树，
   按字段号取值。**字段号是接口契约，比 DOM class 稳得多。**

还有一条结构性的：**历史不要从业务侧读**。抖音网页是虚拟列表（DOM 里只有最近约 20 条），
它把注入过的消息全留在 DSH 的 session 日志里，`douyin_history` 读的是那边。

## 对 wx-bridge 有用的三条

| 教训 | 出处 | 我们怎么用 |
|---|---|---|
| 动作要用**效果**验证，不能看代理信号 | 「发消息只看输入框空不空会假成功」 | `wxuia.send_text` 现在发完会读消息列表核对（`confirm_sent`） |
| 选择器失效要**报错**，不能静默降级 | 坑 14 | UIA 找不到控件时我们已经在返回原因，别改成「尽量试试」 |
| 用**稳定锚点**，不用 hash class | 坑 13（`data-e2e`） | UIA 侧对应 AutomationId / ControlType，不是坐标和 class 名 |

## 不该学的地方

- **`mirror` 模式会重复发**（agent 自己发的内容又被回发一遍）。它自己在 README 里标了
  「同一时刻只用一种模式」——这是设计没收敛，不是配置问题。
- **发消息的接口路没做**（要自己拼 protobuf + 签名，成本高）。所以它的「发送」仍然走
  DOM，也就仍然脆。**读走接口、写走 DOM** 是它现在的真实形态，不是理想形态。
- **风控是绕不过的**：发评论会要短信验证码，返回 `NEEDS_VERIFY` 并带上被遮的手机尾号。
  它没有假装成功 —— 这点值得学（报错要具体）。

## 如果真要接到我们这边

三个选项，代价差一个数量级：

1. **不接**，只抄上面三条工程教训（已完成）。
2. **抄读法**：如果我们哪天需要读某个网页端的数据，用「hook 页面自己的请求 + 通用 pb 解码」
   这套，比写爬虫稳，也不用碰签名。
3. **真接抖音**：得装 DSH 插件 + 用户自己的号 + 浏览器常驻。**好友私信会进模型上下文**，
   隐私是首要问题，不是技术问题。
